## 观察证据

- 同一测试夹具在 Windows 因全局默认分支为 `main` 通过，在 GitHub Linux Runner 因 bare 仓库默认
  `HEAD=master` 失败；主线在修复前出现一次可由候选 Linux CI 提前拦截的红灯。
- `release-kpanel` 已要求产品候选 CI 先于主线，但 `evolve-kpanel` 只要求本地治理门禁和正常集成授权，
  没有把同一要求应用到治理变更自身。
- 已确认根因是治理集成路径缺少远端候选证据，不是 Git 冲突、产品代码失败或生产环境故障。
- 未确认项：共享管理工作树的 10 个未提交文件归属；本提案不触碰该现场。

## 原因假设

- 根因：治理路径把本地 `verify-governance` 视为主线前最终证据，未要求受支持 Linux 环境对同一 SHA
  先运行 CI。
- 替代解释：若失败来自不可控上游瞬时故障，则固定候选门禁收益有限；本次失败可由确定性 Linux
  夹具复现，排除该解释。
- 证伪条件：候选 CI 无法在不增加普通产品/文档任务成本的前提下只对治理变更生效，或主线无法可靠
  识别同一 SHA 的成功候选证据。
- 不涉及 `kejilion.sh`、Panel/Agent、真实主机资源或产品兼容契约。

## 产品原则与核心思想对齐

- 不改变业务真源、双端互通、运行资源或用户能力。
- 只在治理路径增加一次既有 Linux CI，不增加常驻服务、生产依赖或第二状态源。
- API 查询只发生在 GitHub 主线 CI，使用仓库临时 Token 和只读 `actions: read`；Token 在
  `verify-change.sh` 入口从通用环境删除，只临时注入候选查询子进程。本地 Git 开发仍不依赖 GitHub API
  或 `gh` 登录。

## 备选方案与取舍

| 方案 | 收益 | 风险 / 成本 | 结论 |

## 最小改动方案

- `verify-change.sh` 已拥有治理路径唯一分类，仅在 `CI=true` 且 `main` 时调用候选证据检查，不复制路径表。
- 新脚本固定查询 `ci.yml`、精确 SHA 和允许的候选分支前缀；缺失、失败、SHA 漂移或 API 不可用均失败。
- 候选 CI 本身不查询远端证据，避免递归；本地和普通产品路径无额外网络成本。
