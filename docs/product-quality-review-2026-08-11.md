## 项目性质

KPanel 是与 `kejilion.sh` 双向互通的 Linux 服务器管理控制面，而不是普通 Web 内容后台：

1. 浏览器连接非 root `paneld`，宿主机写操作只能经 Unix Socket 上的结构化 Agent 执行；
2. Docker Engine、Nginx、systemd、系统文件和 `kejilion.sh` 产物是真实业务状态，Panel 存储只保存
   账户、Session、审计、任务索引和必要缓存；
3. 脚本、SSH、Compose、CLI 和 Web 创建的资源必须互相发现并继续管理，来源不能成为授权条件；
4. 产品直接面向低配 Linux 主机，单文件 Go Agent、非 root scratch 镜像、资源上限和双架构属于
   用户价值，不只是实现细节；
5. 安装、更新、网站、应用、Docker、文件、终端和系统动作可能改变生产主机，因此正确成功判定、
   失败恢复和回滚证据与功能本身同等重要；
6. 管理员应获得底层工具真实支持的完整能力，安全控制必须防未授权、注入、篡改、竞态、泄密和
   耗尽，不能重新引入“危险所以不让操作”的产品护栏。

## 业务规模与核心旅程

基线仓库包含 21 个后端领域目录、505 个 `internal/` 与 `web/src/` 文件，前端公开路由覆盖初始化、
登录、总览、监控、进程、集群、AI、网站、环境、应用、文件、终端、体检、Docker、活动记录和设置。
主要高风险业务域及其验收重心如下：

| 业务域 | 业务真源 | 主要风险 | 必要用户证据 |
| --- | --- | --- | --- |
| 系统管理 | systemd、系统文件、固定脚本协议 | 失联、配置半写、发行版差异 | 写前备份、失败回滚、写后回读、脚本继续管理 |
| 网站与环境 | `/home/web`、Nginx、LDNMP | 模板漂移、证书/配置损坏 | `nginx -t`、双端互通、外部配置来源一致 |
| 应用市场与体检 | `kejilion.sh`、Docker、后台任务 | 第三方脚本、长任务、资源消耗 | 固定 selector、真实进度、断线恢复、失败清理 |
| Docker 与文件 | Docker Engine、`/home` | 高权限删除、路径/归档、数据量 | 外部资源可管理、路径边界、资源版本、恢复副本 |
| 集群与终端 | HTTPS/Noise、PTY、Agent | 远程权限、明文、会话泄漏 | 配对/撤销、scope、输入输出上限、断线恢复 |
| AI 运维 | Provider API、固定 KPanel 工具 | 模型兼容、工具越权、错误恢复 | Schema 可移植、写入确认、固定工具、恢复语义 |
| 桌面与移动交互 | 浏览器实时状态 | 输入被遮挡、焦点丢失、布局回归 | 双视口、键盘/焦点、浅深色、多语言、错误态 |

## 更新节奏事实

从 2026-07-25 首个提交到 2026-08-10 的当前基线：

- `origin/main` 共 521 个提交；提交类型为 `fix 140`、`feat 123`、`docs 120`、`chore 100`，其余
  为测试、CI、性能、样式、构建、发布和少量重构/策略提交；
- 仓库共有 124 个 `v*` 标签，16 个有标签日期的自然日中单日发布 1–13 个版本；
- `docs/` 中有 90 份版本验收记录，34 个历史标签没有同名验收文件；现有记录格式随项目演进变化，
  不能稳定机器聚合；
- 最近 100 个主线提交中 `desktop` 37 个、文档 21 个、版本准备 18 个；近期节奏已从大规模底层能力
  扩展转向桌面交互、终端可用性和体验修复，同时仍穿插系统资源协议等高风险能力；
- 最新完整质量审计基线是 `v0.38.2`，当前为 `v0.60.2`；自动测试数量和业务页面显著增长，说明
  性能、体验和故障恢复基线需要持续更新，不能永久复用一次审计结论。

高频发布本身不能证明质量差。它同时可能代表小批量、低恢复成本，也可能造成候选重复、生产部署
疲劳和证据形式化。应同时观察部署频率/交付时长与变更失败率/恢复时间，并记录同一问题连续 patch
的原因，不能只用“每天发布几次”决定收紧或放宽流程。

## 现有优势

- L0–L3 风险分级、`make verify-change`/`make verify-release` 和候选/主线/Release 三层远端门禁已经存在；
- 自动覆盖 Go/Web、race、`govulncheck`、`npm audit`、Trivy、双架构、最终镜像和受限容器契约；
- Release 产物包含 SHA-256、SBOM、provenance、源码修订和公开镜像 E2E；
- 多数近期版本记录生产备份、健康检查、Agent/镜像一致性、数据完整性和精确回滚点；
- 产品规则已经正确区分“管理员合法能力”与“网络入侵防护”，并把真实状态和双端互通设为硬规则。

## 需要补强的地方

1. 现行质量规范主要以性能、稳定、安全和资源命名，用户体验、可访问性、业务正确性虽分散存在，
   但没有进入同一证据模型；
2. 逐版本记录格式不统一，自动测试、隔离真机、公开产物和生产观察有时混在同一“通过”结论中；
3. 性能预算明确，但受影响基准的执行和历史比较仍主要依赖专项审计；
4. 生产环境通常没有管理员浏览器逐按钮或危险写操作验收，这是合理安全选择，但必须与隔离真机证据
   分开记录，不能写成全功能生产验收；
5. 发布节奏没有统一数据反馈：部署频率可从标签推导，但变更失败率、恢复时间、紧急热修复和重复
   发布原因尚未结构化记录；
6. 单一 Debian 13 主机证据较强，其他声明支持的发行版多数仍是“已实现待实机准入”，不能用通用
   Linux 构建替代正式支持结论。

## 本次规范决策

- 质量模型扩展为业务正确性、性能、稳定性、资源、安全、用户体验六维；
- 以受影响业务域和核心用户旅程选择验收，不为纯展示改动强制无关生产写操作；
- 统一“已验证、已实现未实机验证、未实现、不适用”状态，并区分自动、隔离真机、公开产物、生产；
- 引入发布画像和统一验收模板，记录变更面、证据、不适用维度、遗留风险和回滚；
- 不设置主观最短发布间隔；滚动采集交付速度与稳定性指标，先建立基线，再用趋势调整节奏；
- 用户体验按可完成任务验收，纳入桌面/移动、浅/深色、键盘/焦点、缩放、多语言和失败恢复；
- 保留现有性能、安全和容器硬门禁，不因新增体验维度削弱宿主机管理产品的安全边界。
